# Red team review: failure modes (Flow Tracer)

Plan: `plans/261030-1009-license-gioi-han-so-lan/` (plan.md + phase-01..06). Code traced: `dema4_rs/src/gui.rs`, `gui_tach/nut_tach.rs`, `main.rs`, `telegram.rs`, `tach_vb/du_lieu_an.rs`, `tach_vb/tach.rs`, `cau_hinh.rs`.

## Finding 1: `ghi_lan` / `ghi_bu` are not idempotent, so timeouts cause double counting
- **Severity:** Critical
- **Location:** phase-02 Requirements (ScriptLock waits up to 10 s; `ghi_bu` sends a bare `n`), phase-03 Requirements (4 s client timeout), phase-04 Architecture `da_chay` (on error, `BoDemOffline::cong`)
- **Flaw:** The client gives up after 4 s. The relay can wait 10 s for the lock, plus 3–5 s for a cold start, and then append the log row anyway. The client treats any error as "not recorded" and adds 1 to the offline counter. The next successful call sends `bu_offline = n`, and the relay appends n more rows. Nothing deduplicates them.
- **Failure scenario:** Cold start (4.5 s) on the first Đếm of the day. The relay writes row 1 and the client times out, so the offline counter goes to 1. On the second Đếm, `ghi_lan(bu=1)` writes rows 2 and 3, so the count reaches 3 of a limit of 2. A trial user loses the second run. Test 5c (`tram_qua_tai_khong_mat_luot`) locks in this bug: it assumes a 503 or timeout means "not written". Matrix row 16 (20 machines, 503s "ghi bù sau") will over-count too.
- **Evidence:** plan phase-02-tram-apps-script.md:21 (lock 10 s → 503), :67 (cold start 3–5 s); phase-03-kho-tram-va-bo-khoa-sheet.md:17 (timeout 4 s); phase-04-gan-license-gui-va-dong-lenh.md:27, :46. The existing app already uses a 4 s timeout pattern at dema4_rs/src/telegram.rs:94.
- **Suggested fix:** The client generates a usage ID (16 random bytes) once per run and keeps it in the pending journal (Finding 2). `ghi_lan` and `ghi_bu` send the list of IDs, and the relay skips IDs it has already logged (log column + `CacheService` lookup). The offline file stores pending IDs, not counts. Remove pending IDs only after the signed response echoes them back. Set the relay lock wait below the client timeout (for example 3 s), or raise the client timeout to more than lock wait plus cold start.

## Finding 2: Usage is saved only after a background network attempt, so closing the app loses the count. Tách can be taken for free by quitting before it finishes
- **Severity:** Critical
- **Location:** phase-04 Architecture (`da_chay` spawns a thread for `ghi_lan`; `BoDemOffline::cong` only runs on error); "Điểm chạy xong" hook in `nhan_ket_qua_tach`
- **Flaw (a):** Nothing is written to disk until the thread has finished its network call (up to 4 s). When eframe returns from `run_native`, the process exits and detached threads die. Offline, a user who closes the app right after the result popup is never counted, and the offline limit of 2 never triggers.
- **Flaw (b):** The Tách worker writes output PDFs to disk one hồ sơ at a time. The count only happens in `nhan_ket_qua_tach`, after the worker sends its result. The app itself offers "Thoát luôn" while Tách is running. The user watches the progress popup reach 100% (or near it), clicks Thoát luôn or kills the process, and keeps the split files without using a run. Đếm has the same problem in a weaker form: closing is not guarded during Đếm at all.
- **Failure scenario:** (a) Cable unplugged: Đếm, close, reopen, Đếm, close, and so on. This gives unlimited offline Đếm runs. (b) Any trial user with an exhausted quota can run Tách unlimited times, with no technical skill needed.
- **Evidence:** dema4_rs/src/gui.rs:104-129 ("Thoát luôn" → `ViewportCommand::Close`), dema4_rs/src/gui.rs:249-256 (close guard checks only `self.tach.dang_chay()`, not Đếm); dema4_rs/src/gui_tach/nut_tach.rs:294-301 (detached worker), :305-316 (count point reached only after `try_recv` succeeds); dema4_rs/src/tach_vb/tach.rs:158, :199-204 (per-hồ sơ directory and file writes inside the loop); plan phase-04-gan-license-gui-va-dong-lenh.md:27, :31.
- **Suggested fix:** Write a reservation synchronously to both offline files before spawning the worker, in `bat_dau_dem` / `bat_dau_tach` and in the CLI. At completion: if there was no result, refund it; otherwise mark it "chờ ghi". Only a signed ack clears it. On next start, any leftover reservation counts as used, and gets sent through `ghi_bu` with its ID (Finding 1). Add tests: kill after the reservation, then restart. The counter must be ≥ 1.

## Finding 3: Races in `KiemTra`: shared counters reset on any response, responses arrive out of order, `xoa` wipes concurrent increments, and processes overwrite each other's files
- **Severity:** High
- **Location:** phase-04 Architecture `lam_moi_ngam` / `da_chay` (`chay_tu_ban_sao = 0` on every response; "ghi bù rồi `xoa`"); phase-01 `BoDemOffline::cong` / `xoa`
- **Flaw:** Several network calls can be in flight at once: `lam_moi_ngam` at startup, `da_chay` for Đếm, `da_chay` for Tách, and Kiểm tra lại. Each one sets `ban_sao` to its own response and resets `chay_tu_ban_sao` to 0. The plan has no sequence number, no pending counter per request, and no max().
- **Failure scenarios:**
  - The startup `kiem_tra` is slow (cold start). The user runs Đếm, so `chay_tu_ban_sao.dem = 1`. Then the `kiem_tra` response arrives with a snapshot from before the run and resets the local count to 0. The user gets an extra run, which breaks the invariant test 3 (`khong_chay_lo_khi_chua_ghi_kip`) claims to protect.
  - Two `ghi_lan` responses arrive out of order. The older one (da_dung = 1) overwrites the newer one (da_dung = 2), so the cache moves backwards.
  - Thread A reads offline n = 1 and sends `ghi_bu(1)`. Meanwhile thread B fails and calls `cong`, so the file holds 2. Thread A then calls `xoa`, and B's count is lost. Or A and B both read n = 1 and both send `ghi_bu(1)`, which double counts.
  - Two windows or processes do read-modify-write on the same two files with no lock, so they lose increments. The plan's "lố tối đa số cửa sổ − 1" understates this, because the offline state is corrupted too.
- **Evidence:** plan phase-04-gan-license-gui-va-dong-lenh.md:24-28, :64; phase-01-loi-license.md:33, :37. The fire-and-forget threads the plan copies are at dema4_rs/src/gui.rs:853-855 and dema4_rs/src/gui_tach/nut_tach.rs:162.
- **Suggested fix:** Track pending usage IDs per request instead of one shared counter. When a response arrives, remove only the IDs it acknowledges, and keep `max(da_dung)` per function plus a monotonic sequence. Do all network calls through one serialized worker thread (an mpsc queue) so responses cannot interleave. Replace `xoa` with "remove the acknowledged IDs". Write offline files with an advisory lock (`fs2`/`fd-lock`) and atomic rename. Add tests that interleave a slow `kiem_tra` with `da_chay`.

## Finding 4: The offline rule ignores the last known state, so an exhausted or Khoá machine gets free runs at every launch and every network toggle
- **Severity:** High
- **Location:** phase-01 `quyet_dinh` ("online None → offline.cn < 2 thì Cho"); phase-04 `quyet_dinh(cn)` ("chưa có → luật offline"); `ban_sao` is memory-only
- **Flaw:** `ban_sao` is never saved to disk. From app start until the startup `kiem_tra` succeeds (3–5 s cold start, or never if the relay URL is blocked), decisions use only the offline rule. That rule allows 2 runs regardless of whether the machine is Khoá or out of quota. After `ghi_bu` succeeds, `xoa` resets the offline counter to 0. The relay records the overuse but nothing enforces it.
- **Failure scenario:** A machine marked Khoá blocks `script.google.com` in hosts or a firewall, and gets 2 runs. It unblocks, the app opens, and `ghi_bu` clears the counter. It blocks again and gets 2 more runs, indefinitely. An ordinary user can get the same effect by opening the app and clicking Đếm within 2 s, before the cold-start response arrives: 1 free run per launch. This contradicts the plan-level criterion "đặt Khoá → chặn ngay khi mở lại app".
- **Evidence:** plan phase-01-loi-license.md:38; phase-04-gan-license-gui-va-dong-lenh.md:24-26; phase-02-tram-apps-script.md:67 (cold start 3–5 s); plan.md:41 (the Khoá acceptance criterion).
- **Suggested fix:** Save the last signed `{du_lieu, chu_ky}` to both license locations. It cannot be forged, only deleted. On start, verify it and load it as `ban_sao`. Offline decision = min(offline rule, cached remaining quota), and Khoá stays Khoá while offline. Clear offline counts only by the acknowledged IDs, never with a blanket `xoa`.

## Finding 5: The machine ID is built from unstable inputs, so paying customers get blocked and trial users get fresh trials
- **Severity:** High
- **Location:** phase-01 Requirements ("không đổi khi bật VPN / cắm thêm card") versus Architecture ("SHA-256 of `ten|mac|ma_hdh`", which reuses `telegram::ten_pc`, `dia_chi_mac`)
- **Flaw:** `dia_chi_mac()` calls `mac_address::get_mac_address()`, which returns the first non-loopback interface the OS lists. That changes with VPN adapters (TAP/WireGuard), USB-Ethernet docks, Wi-Fi vs LAN, Hyper-V/Docker vSwitches, and on macOS with Wi-Fi off. `ten_pc()` is `whoami::devicename()`, which a user can rename. The plan's own requirement contradicts the inputs it hashes.
- **Failure scenario:** A "Đã cấp" customer plugs in a dock. The ID changes, the relay auto-registers a new "Dùng thử" row, and on the third run the paying customer is blocked. Meanwhile any user can rename the PC to get 2+2 new runs, and the `license` tab fills with duplicate rows.
- **Evidence:** dema4_rs/src/telegram.rs:70-72 (`whoami::devicename`), :75-80 (`mac_address::get_mac_address`, first interface); plan phase-01-loi-license.md:16, :29, :36.
- **Suggested fix:** Hash only the OS identifier (MachineGuid / IOPlatformUUID). If that cannot be read, generate a random ID once and save it in both license locations. Send the name and MAC only as informational columns. Add a test where changing the MAC does **not** change the ID. The current test 1 asserts the opposite, which is the bug.

## Finding 6: The hook points sit on structs that cannot see `UngDungChinh`, and the existing tests and CLI tests would hit the real relay and change real counters
- **Severity:** High
- **Location:** phase-04 Architecture ("`UngDungChinh` giữ `Arc<KiemTra>`; `quyet_dinh` ở đầu `gui.rs::bat_dau_dem` và `nut_tach.rs::bat_dau_tach`"; "Test GUI cũ: `UngDungChinh` tạo `KiemTra` với `KhoGia`")
- **Flaw:** `bat_dau_dem` and `luu_va_thong_bao` are methods on `UngDung`. `bat_dau_tach` and `nhan_ket_qua_tach` are methods on `ManTach`. Both structs are built with `Default` and have no access to `UngDungChinh`. Tests build `UngDung` directly (`app_mau`) and call `luu_va_thong_bao` or `bat_dau_dem` on it. The CLI tests call the real `chay_tach` and expect exit code 0. `BoDemOffline` uses real paths: `<exe dir>/.sm-dema4`, which for `cargo test` is next to the test binary, and `%APPDATA%/sm-dema4`.
- **Failure scenario:** `cargo test` runs `chay_tach` through `KhoTram` against production. That consumes the dev machine's quota, adds rows to the real `license_nhat_ky`, and increments the developer's real offline files. After 2 offline test runs, `tach_ap_goc_xoay_va_ghi_log` and `tach_chua_co_nhan_thi_phan_tich_tu_dong` start returning 3, so the CI result depends on history. The plan's statement that tests make no real network calls (plan.md acceptance) cannot be met as designed.
- **Evidence:** dema4_rs/src/gui.rs:75-79, :94 (`tach: Default::default()`), :465, :501 (`impl Default for UngDung`), :685, :837, :1382-1395, :1600, :1621; dema4_rs/src/gui_tach.rs:217 (`impl Default for ManTach`); dema4_rs/src/main.rs:197, :218; dema4_rs/src/tach_vb/du_lieu_an.rs:56-63; dema4_rs/src/cau_hinh.rs:316-325; plan phase-04-gan-license-gui-va-dong-lenh.md:29, :33.
- **Suggested fix:** Store `Arc<KiemTra>` in `UngDung` and `ManTach`, injected from `UngDungChinh`. In `cfg(test)`, `Default` should build `KhoGia` with temp-dir `BoDemOffline` paths. Make `chay_tach` and `chay_dong_lenh` take `&KiemTra` (with a thin `main` wrapper). Add a guard test that fails if any `cfg(test)` code path builds `KhoTram`.

## Finding 7: CLI gaps: `--khong-ghi` returns full results before any count point, and the exit and error paths are undefined
- **Severity:** High
- **Location:** phase-04 Architecture CLI line ("đọc đồng bộ 1 lần … `da_chay` ghi đồng bộ trước khi thoát"); plan.md decision "Áp cho cả … đếm CLI"
- **Flaw:** `chay_dong_lenh` prints the whole result (`kq.tong_hop`) and returns 0 when `--khong-ghi` is set, before saving. The plan defines the Đếm count point only for the GUI (`luu_va_thong_bao`). `chay_tach` returns 1 when `kq.loi` is non-empty, but output files were still written, and the plan does not say whether that run counts. The CLI also has no reservation, so Ctrl-C after output is printed but before the synchronous `ghi_lan` finishes means no count.
- **Failure scenario:** The user runs `sm-dema4 <dir> --khong-ghi` in a loop and gets unlimited Đếm results, already documented in the module header as a "đo tốc độ" mode. Or `--tach` on a folder with one broken PDF writes 200 documents, exits 1, and possibly is not counted.
- **Evidence:** dema4_rs/src/main.rs:8 (documents `--khong-ghi`), :72-75 (`print!` then `return 0` before save), :159-173 (files written; exit 1 when `loi` is non-empty), :38 / :43 (`process::exit` right away).
- **Suggested fix:** Count at "result produced" (`SuKien::Xong` with ≥ 1 file / `kq.dong` non-empty), regardless of `--khong-ghi` or the exit code. Use the reservation from Finding 2 before starting work. Add CLI tests for `--khong-ghi` when out of quota (blocked) and for a Tách with partial errors (counted).

## Finding 8: The Telegram queue trigger fights with `doPost` over the lock and may send duplicates, while counting from the log makes every call slower over time
- **Severity:** High
- **Location:** phase-02 Requirements (queue `guiHangDoi` every minute, 15 messages per run; `getScriptLock` while writing, ≤ 10 s; usage "đếm từ nhật ký", recomputed on every write)
- **Flaw (a):** The plan does not say whether `guiHangDoi` takes the script lock. If it does, 15 sequential UrlFetch calls (each ~0.5–1 s, and `sendDocument` with a CSV is slower) hold the lock for more than 10 s every minute. Every `ghi_lan` in that window gets a 503, which feeds the double counting in Finding 1. If it does not, a run that takes longer than 1 minute (Telegram slow, 15 × 15 s timeouts) overlaps the next trigger run. Both read the same "chờ" rows and send them twice. Concurrent `appendRow` calls from `doPost` also shift row indexes while `guiHangDoi` is updating status by index.
- **Flaw (b):** "15 tin" counts queue rows, but `thong_ke_tach` sends 2 Telegram API calls (text plus CSV document). 15 Tách rows means 30 calls per minute to one group, which is over the ~20 per minute limit the plan cites. That causes a 429 every cycle, and the queue grows without bound at peak.
- **Flaw (c):** Recomputing "Đã dùng" by scanning `license_nhat_ky` on every write is O(log rows) while holding the lock. The log grows forever with no cleanup, so lock hold time rises until calls regularly exceed the client's 4 s timeout.
- **Evidence:** plan phase-02-tram-apps-script.md:17, :19, :21, :22, :32; the app sends text and a CSV per Tách today at dema4_rs/src/gui_tach/nut_tach.rs:170 (`gui_tin`) and :186 (`gui_file`).
- **Suggested fix:** Keep a separate short lock section in `guiHangDoi` that claims rows ("đang gửi" plus a lease timestamp), releases the lock, sends, then re-locks briefly to mark rows "đã gửi". Address rows by a stable ID, not by index. Budget Telegram API calls (≤ 15 per run), not rows. Keep running counters in the `license` row (incremented under the lock) and treat `license_nhat_ky` as an append-only audit log that is never scanned on the hot path. Add a test that runs `guiHangDoi` overlapping itself and checks no message is sent twice.

## Finding 9: Old exe versions are a complete bypass that stays public after the service account is revoked
- **Severity:** High
- **Location:** phase-05 steps 8–9; phase-06 Risk ("Bản cũ ≤ v0.5.x mất ghi thống kê … chấp nhận"); plan.md goal ("chặn người dùng phổ thông")
- **Flaw:** The plan treats revoking the service account and the old bot token as losing only statistics. v0.5.x has no license check at all, and its release assets stay downloadable from the public repo. Revoking credentials does not affect the core features.
- **Failure scenario:** A blocked user downloads v0.5.x from GitHub Releases and gets unlimited Đếm and Tách. That is exactly the "người dùng phổ thông" the plan says it stops, and it needs no rebuild.
- **Evidence:** dema4_rs/src/main.rs:28-52 (current entry point: no gate before `chay_tach`, `chay_dong_lenh` or `gui::chay`); plan phase-05-trien-khai-tram.md:30-31; plan.md:21.
- **Suggested fix:** Add a release step: delete or hide the binary assets of releases before v0.6.0 (keep the source tags). State explicitly in the plan that old exe files already on users' machines stay unlimited (accepted risk, owner sign-off). Make Phase 6 success criteria check that "Release page has no pre-0.6 binaries".

## Finding 10: "Chạy xong có kết quả" is ambiguous for Dừng, partial errors and failed saves, and the planned hooks count stopped runs
- **Severity:** Medium
- **Location:** plan.md decision ("1 lần = 1 lần bấm … chạy xong và có kết quả"); phase-04 "Điểm chạy xong có kết quả"
- **Flaw:** `luu_va_thong_bao` also runs after Dừng (`da_dung = true`) and when saving the result file fails. `nhan_ket_qua_tach` runs after Dừng with a partial `kq.dong`. With the plan's hooks, pressing Dừng by mistake after 1 file uses up 1 of the 2 trial runs. Meanwhile the Tách `Err` path (panic or "luồng tách dừng bất thường") is never counted, even though output files may already be on disk. No test covers Dừng, save failure, or worker error.
- **Failure scenario:** A trial user starts Đếm on the wrong folder, presses Dừng after 1 file, and has 1 run left without ever getting a useful result. That produces support calls. Or the Tách worker panics after writing 90% of the files: nothing is counted and the user keeps the output.
- **Evidence:** dema4_rs/src/gui.rs:832-833 (`da_dung` read, then `DaXong` returned for stopped runs), :837-847 (counting continues after `luu_ket_qua` fails), :1346-1347; dema4_rs/src/gui_tach/nut_tach.rs:313-316 (Err → return, no count), :322 (stopped run takes the normal path).
- **Suggested fix:** The owner decides explicitly and the plan writes it down. For example: Dừng counts only if ≥ N% done or ≥ 1 complete file is saved, or never. A save failure does not count. A Tách `Err` with files written counts. Add tests in phase 4 for each case, using the reservation and refund from Finding 2.

Status: DONE
Summary: The plan has 10 failure-mode gaps. The two critical ones are non-idempotent usage recording, where client timeouts lead to double counting, and counts saved only after a network attempt, so quitting the app (including the built-in "Thoát luôn" during Tách) loses or skips the count. Both need a synchronous reservation plus usage IDs before Phase 4 starts.

## Unresolved questions
- Should a Dừng run or a partially failed run count as a use? This is a business decision (Finding 10).
- Are old binaries on users' machines an accepted bypass, and should old GitHub release assets be removed (Finding 9)?
