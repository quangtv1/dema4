# Red team: Assumption Destroyer + Scope Auditor — plan 261030-1009-license-gioi-han-so-lan

Verified against: `dema4_rs/` sources, `Cargo.toml`, `Cargo.lock`, `~/.cargo/registry` (ureq 3.5.0, ureq-proto 0.6.5, rsa 0.9.10), `git log`, `gh repo view` / `gh release list`.

Checked and not raised: ureq 3 does follow Apps Script's POST→302→GET (`ureq-proto-0.6.5/src/client/redirect.rs:19-68` changes POST to GET on 301/302). `openssl genpkey` gives PKCS#8 PEM, which is the format `Utilities.computeRsaSha256Signature` expects.

## Finding 1: Retried writes can bill one run twice: client timeout is shorter than cold start, and both threads send the same pending offline count
- **Severity:** Critical
- **Location:** Phase 3 Requirements (4 s timeout); Phase 4 Architecture (`lam_moi_ngam`, `da_chay`); Phase 2 Requirements (`ghi_lan`, `ghi_bu`)
- **Flaw:** The plan assumes a failed call means nothing was written. Apps Script runs `doPost` to completion before it sends the 302, so the client can time out after the row is already in the log. The plan's own cold-start figure (3–5 s) is above the 4 s client timeout. On error, `da_chay` adds 1 to the offline counter, and that run is later sent again as "bù offline". Also, `lam_moi_ngam` and `da_chay` both attach "lần offline chờ" and only clear the counter after success. With no request ID and no server-side dedup, two calls can both send the same pending `n`.
- **Failure scenario:** A trial machine opens the app (cold start, 4.5 s). The user clicks Đếm and finishes. `ghi_lan` is written on the server but the client times out, so offline goes to 1. On the next open, `ghi_bu n=1` is sent. The log now has 2 rows for 1 run, and the user sees "Số lần Đếm còn lại (0)" after only one real run. Case 2: the user finishes a run while the startup `lam_moi_ngam` is still in flight. Both calls carry `bu_offline=2`, so the server records 4 extra uses. "Không mất lượt" is protected, but the opposite case (charging the customer twice) is not tested anywhere.
- **Evidence:** plans/261030-1009-license-gioi-han-so-lan/phase-03-kho-tram-va-bo-khoa-sheet.md:17 (timeout 4 s); phase-02-tram-apps-script.md:67 (cold start 3–5 s); phase-04-gan-license-gui-va-dong-lenh.md:26-27 (both paths send pending bù); phase-04-gan-license-gui-va-dong-lenh.md:46 (test 5c checks only the under-count direction); dema4_rs/src/telegram.rs:93-95 (`ip_public` takes up to another 4 s before the station call when `ThongTinMay` is filled)
- **Suggested fix:** Give each use a client-generated ID (UUID, saved in the offline file next to the counter). `ghi_lan` and `ghi_bu` send a list of IDs. The station skips IDs that are already in `license_nhat_ky`. Keep a single-flight flag in `KiemTra` so only one write is in flight at a time. Add a test where KhoGia "writes, then returns Err" and expect `da_dung` to grow by exactly 1. Raise the timeout to at least 10 s for background calls, keep 4 s only for the UI wait, and do not block on `ip_public` (fill it on the server side or cache it).

## Finding 2: The license can be bypassed by downloading an older release, and the plan delays revoking the key with no end date
- **Severity:** Critical
- **Location:** Phase 5 steps 8–10; Phase 6 step 5; plan.md "Quyết định đã chốt"
- **Flaw:** (a) v0.4.x/v0.5.x are public GitHub releases with no license check. Any ordinary user can download v0.5.2 and keep using it, which defeats the main goal ("chặn người dùng phổ thông"). The plan does not mention removing or hiding the old assets. (b) The v0.5.x exes contain the service-account key, which has edit rights on Monitor_dema4. Until it is revoked, anyone who extracts it can edit the new `license` tab and grant themselves "Đã cấp" (the exact threat the plan targets: "chặn cố tình … tự cấp quota trên Sheet"). They can also read the `Cấu hình` tab that will hold the new Telegram token. The plan waits for "các máy đã cập nhật", which has no end date. (c) The current Telegram token is committed in a public repo, so it is already exposed. Tests 6/7 only remove it from HEAD.
- **Failure scenario:** Phase 5 goes live. A user with v0.5.2 extracts `private_key` with `strings`, gets an OAuth token, writes `L=Đã cấp, J=9999` for their own machine ID, and uses v0.6.0 without limit. Or they simply reinstall v0.5.2 from the Releases page.
- **Evidence:** `gh release list -R quangtv1/dema4` shows v0.5.2/v0.5.1/v0.5.0/v0.4.x as public; `gh repo view` reports visibility PUBLIC; dema4_rs/src/telegram.rs:31 (token in source, present in history since commit d702e51); dema4_rs/build.rs:8 + .github/workflows/build.yml:64 (SA key embedded in CI exes); plans/261030-1009-license-gioi-han-so-lan/phase-05-trien-khai-tram.md:30-31 (revoke only "sau khi … các máy đã cập nhật")
- **Suggested fix:** Revoke the service-account key and rotate the bot token at the same moment the station goes live, not afterwards. Losing statistics from old versions is already accepted. Delete or replace the release assets from ≤ v0.5.2, or accept and write down that downgrading is an open bypass. Add a server-side minimum-version check so old builds fail loudly instead of quietly.

## Finding 3: The machine ID includes MAC and PC name, which contradicts the plan's own "stable" requirement and makes trial reset trivial
- **Severity:** High
- **Location:** Phase 1 Requirements and Architecture (`ma_may_tu(ten, mac, ma_hdh)`, SHA-256 of `ten|mac|ma_hdh`)
- **Flaw:** `dia_chi_mac()` uses `mac_address::get_mac_address()`, which returns the first non-loopback interface. That choice depends on interface order (VPN/TAP adapters, USB NICs, Wi-Fi vs Ethernet) and on randomized/private Wi-Fi MACs. `ten_pc()` is the computer name, which the user can change. Hashing both into the ID means it changes in exactly the cases the requirement says it must not.
- **Failure scenario:** A licensed customer turns on a VPN or docks a laptop. The MAC changes, the app sees a new machine with 2/2 trial, and the paid license appears gone (support ticket). A trial user renames the PC and gets 2+2 new runs, repeatable without limit. No technical skill is needed.
- **Evidence:** plans/261030-1009-license-gioi-han-so-lan/phase-01-loi-license.md:16 ("không đổi khi bật VPN / cắm thêm card mạng") vs :29,:36 (hash includes `ten|mac`); dema4_rs/src/telegram.rs:70-80 (`whoami::devicename`, `get_mac_address` first interface)
- **Suggested fix:** Hash only MachineGuid / IOPlatformUUID. Fall back to name+MAC only when the OS ID is empty, and mark that case (for example prefix `SM-X`). Send name and MAC as information only. Add a test showing the same OS ID with a different MAC gives the same ID.

## Finding 4: Apps Script cannot return HTTP 503, and the plan's error contract and smoke test both assume it can
- **Severity:** High
- **Location:** Phase 2 Requirements (lock timeout → "trả lỗi 503"); Phase 4 test 5c; Phase 6 matrix #16; Phase 5 Success Criteria (`curl -X POST`)
- **Flaw:** `ContentService` output is always 200 after the 302 hop; status codes cannot be set. Script errors and quota errors come back as **HTML pages with status 200**. The plan names no error field in the body, and the Rust contract only specifies `{du_lieu, chu_ky}`. Also, `curl -X POST … -d` without `-L` returns the HTML for the 302. With `-L`, `-X POST` forces POST on the googleusercontent echo URL, which fails. So the stated success check gives a false failure.
- **Failure scenario:** The lock is busy, and the station returns `{loi:"ban"}` with status 200 (or an HTML error page). KhoTram fails JSON parsing or finds no `chu_ky`. That is handled as Err only if the code was written defensively. In KhoGia tests "503" is just an `Err` variant, so the real wire format is never tested. The operator runs the documented curl command, sees "Moved Temporarily", and loses an hour.
- **Evidence:** plans/261030-1009-license-gioi-han-so-lan/phase-02-tram-apps-script.md:21,28; phase-04-gan-license-gui-va-dong-lenh.md:46; phase-06-kiem-thu-tong-va-phat-hanh.md:37; phase-05-trien-khai-tram.md:35
- **Suggested fix:** Define the body contract `{ok:false, loi:"…"}` vs `{du_lieu, chu_ky}`, and treat non-JSON, `text/html`, or a missing `chu_ky` as `Err`. Add Rust tests that use captured HTML error pages and an `{ok:false}` body. Change the curl check to `curl -L -H 'Content-Type: application/json' --data '…' <url>` (no `-X POST`).

## Finding 5: Vietnamese text in the signed data and in hand-typed cells will break signing and the lock without any error
- **Severity:** High
- **Location:** Phase 2 Architecture (`du_lieu.trang_thai`, `computeRsaSha256Signature(du_lieu, KHOA_BI_MAT)`, column L); Phase 6 matrix #4 ("L = Khoá")
- **Flaw:** (a) The plan does not say which charset the signature covers. The default `computeRsaSha256Signature(String, key)` does not document UTF-8. If the station signs non-UTF-8 bytes, Rust verification of the UTF-8 bytes fails only when a value has diacritics. Test 3 in phase 3 uses one captured sample, which is probably a new "Dùng thử" machine or plain ASCII. (b) Column L is typed by hand. Vietnamese has two accepted spellings ("Khoá" vs "Khóa", "Đã cấp" with the accent in a different place) and NFC/NFD input differences on macOS. An exact string compare will not recognize the value and fall back to the empty-cell default, which is Dùng thử.
- **Failure scenario:** The owner types "Khóa" (old tone placement) in L. The station does not match "Khoá", treats it as Dùng thử, and the locked machine keeps running. Or the owner types "Đã cấp" and the signature check fails for every licensed machine, so they drop to the 2-run offline rule.
- **Evidence:** plans/261030-1009-license-gioi-han-so-lan/phase-02-tram-apps-script.md:29,31-32; phase-06-kiem-thu-tong-va-phat-hanh.md:25; phase-01-loi-license.md:23
- **Suggested fix:** In `du_lieu`, send `trang_thai` as an ASCII code (`dung_thu|da_cap|khoa`). Sign with the explicit overload `computeRsaSha256Signature(du_lieu, key, Utilities.Charset.UTF_8)`. Put a data-validation dropdown on column L. Normalize (NFC, lowercase, strip diacritics) before matching, and treat any unrecognized non-empty value as **Khoá**, not Dùng thử. Add a cross-test (phase 3 test 3) with a sample that contains diacritics.

## Finding 6: Scope audit: `KiemTra` is placed on the wrong struct, and existing tests and the CLI bypass it or touch the real disk and network
- **Severity:** High
- **Location:** Phase 4 Architecture ("`UngDungChinh` giữ `Arc<KiemTra>`", "Test GUI cũ: `UngDungChinh` tạo `KiemTra` với `KhoGia` … qua `#[cfg(test)]`"); Phase 1 `BoDemOffline` paths
- **Flaw:** `bat_dau_dem` / `luu_va_thong_bao` are methods on `UngDung`, and `bat_dau_tach` / `nhan_ket_qua_tach` are on `ManTach`. Neither can reach a field on `UngDungChinh`. Tests build `UngDung::default()` and `ManTach { .. Default }` directly and call `bat_dau_dem` / `bat_dau_tach` / `luu_va_thong_bao` without going through `UngDungChinh`. The CLI test calls `chay_tach()` directly, and that will now build a real `KhoTram`. `BoDemOffline` paths point to `<du_lieu_an goc>`, but `goc_du_lieu()` is a private `OnceLock`. When the exe folder is not writable it falls back to `%APPDATA%/sm-dema4/.sm-dema4`, so both "2 nơi" end up under the same `sm-dema4` folder, and one folder delete resets both. `UngDungChinh::default()` is also the production constructor (`chay()`), so any startup `lam_moi_ngam` placed there also runs in about 12 kittest harnesses.
- **Failure scenario:** `cargo test --release`: `tach_ap_goc_xoay_va_ghi_log` calls the real station with the dev machine ID (breaking the "test không gọi mạng thật" criterion and using up dev quota), or gets exit 3 when offline. Parallel tests write to the real `%APPDATA%/sm-dema4/license_offline.txt` and `target/release/deps/.sm-dema4`, which pollutes the developer's real counter and makes tests flaky. In production, a user deletes `%APPDATA%\sm-dema4` and the offline counter is reset.
- **Evidence:** dema4_rs/src/gui.rs:52,90-96 (production and tests share `Default`); gui.rs:685,837 (methods on `UngDung`); gui.rs:1383,1554,1565,1594,1621 (tests build `UngDung::default()` and call `bat_dau_dem`/`luu_va_thong_bao`); dema4_rs/src/gui_tach/nut_tach.rs:273,305,551-556,578,626 (`ManTach` default + `bat_dau_tach` in tests); dema4_rs/src/main.rs:98,177-196 (CLI tests call `chay_tach`); dema4_rs/src/tach_vb/du_lieu_an.rs:56-66 (private `goc_du_lieu` OnceLock, APPDATA fallback); dema4_rs/src/cau_hinh.rs:316-325; plans/261030-1009-license-gioi-han-so-lan/phase-04-gan-license-gui-va-dong-lenh.md:29,33; phase-01-loi-license.md:32
- **Suggested fix:** Add `license: Arc<KiemTra>` to `UngDung` and `ManTach` (or pass it as a parameter to `bat_dau_*` / `luu_va_thong_bao` / `nhan_ket_qua_tach`). Create the real `KiemTra` only in `gui::chay()` and `main()`. `Default` should give a `KhoGia` with a large quota and temp-dir counter paths under `cfg(test)`, and a no-op otherwise. Change `chay_tach` to take `&KiemTra`. Choose 2 storage locations that do not share a parent (for example `%LOCALAPPDATA%` + `%APPDATA%`, or the registry on Windows; `~/Library/Application Support` + `~/Library/Preferences` on macOS). List every changed constructor in the "Related Code Files" section.

## Finding 7: Recounting from the full log on every call, plus unauthenticated registration, makes the station slower over time until clients start timing out
- **Severity:** High
- **Location:** Phase 2 Requirements ("Số lần dùng do trạm đếm từ nhật ký"), Architecture (column I "trạm tính lại mỗi lần ghi"), Risk (rate limit per machine ID only)
- **Flaw:** Every `kiem_tra` / `ghi_lan` reads the whole of `license_nhat_ky` (`getDataRange().getValues()`) while holding the script lock. Cost grows with total usage across all machines. The URL is public and any well-formed `SM-XXXX-XXXX-XXXX` registers a new row. The rate limit is per machine ID, so an attacker just rotates IDs. There is no global cap, no log rotation, and no plan for the 10M-cell limit.
- **Failure scenario:** After a few months there are 50k log rows. Each call takes 2–3 s just to read under the lock. Concurrent callers queue for the lock (up to 10 s), go over the client's 4 s timeout, and every client falls back to the 2-run offline rule (and Finding 1 adds double billing). A script looping over random IDs fills `license` with junk rows and uses up the UrlFetch/trigger quota.
- **Evidence:** plans/261030-1009-license-gioi-han-so-lan/phase-02-tram-apps-script.md:19,21,23,32,70; phase-03-kho-tram-va-bo-khoa-sheet.md:17
- **Suggested fix:** Keep running totals (I/J columns), updated by +1 under the lock with ID dedup (Finding 1). Use the log for audit only. Add a global cap on new registrations per hour via `CacheService`, and archive log rows older than N days. Add a test that seeds 50k log rows and measures `kiem_tra` latency.

## Finding 8: The spreadsheet sits in the TTCNTT Shared Drive, so "chỉ tài khoản Sao Mai thấy tab Cấu hình" cannot hold and "Anyone" access may be blocked by the domain
- **Severity:** Medium
- **Location:** Phase 5 steps 2, 3, 10; plan.md (Workspace decision)
- **Flaw:** Monitor_dema4 lives in the huce.edu.vn Shared drive "TTCNTT". Every member of that drive can read every tab, including `Cấu hình` (bot token) and `license` (they can grant themselves). Per-file access cannot be reduced below drive membership. Step 2's "chuyển quyền sở hữu" does not apply to Shared Drive files, and moving a file between a consumer account and Workspace is a copy that gets a new file ID. On education domains, "Who has access: Anyone" for web apps is often turned off by the admin. The plan does not check this, and the whole design depends on it.
- **Failure scenario:** Deploy shows only "Anyone within huce.edu.vn", so customer machines get the Google login HTML (also Finding 4) and every machine is permanently offline. Or any TTCNTT staff member opens `Cấu hình` and copies the token.
- **Evidence:** repo root `Monitor_dema4.gsheet` under `…/Shared drives/TTCNTT/App/…` (working directory path); plans/261030-1009-license-gioi-han-so-lan/phase-05-trien-khai-tram.md:23-24,32; plan.md:32
- **Suggested fix:** Before phase 2, confirm the "Anyone" deploy option with a 5-line hello-world web app on the target account. Move the token into Script Properties instead of a tab: it stays editable by the script owner and is not visible to Sheet viewers. Or move license data to a separate spreadsheet outside the shared drive, owned by one Workspace account.

## Finding 9: Unstated crate dependencies and setup steps: nonce randomness, Windows registry access, PEM newlines
- **Severity:** Medium
- **Location:** Phase 3 Architecture ("nonce ngẫu nhiên 16 byte", test 1 "tạo cặp khoá RSA trong test"); Phase 1 (MachineGuid "reg query hoặc windows-sys"); Phase 5 step 2 (paste PEM into Script Properties)
- **Flaw:** There is no `rand`/`getrandom` dependency. `rsa::rand_core::OsRng` only works today because another crate happens to enable the `rand_core/getrandom` feature (rsa's own `getrandom` feature is off), which is fragile. Reading the registry through `windows-sys` needs the `Win32_System_Registry` feature, which is not in Cargo.toml. Running `reg query` from a GUI-subsystem exe opens a console window unless `CREATE_NO_WINDOW` is set. The Script Properties field in the UI often loses or mangles multi-line PEM values. If the key is stored as one line, `computeRsaSha256Signature` throws "Invalid argument: key", and nothing in the plan detects that.
- **Failure scenario:** A dependency update removes the transitive feature, and `OsRng` stops compiling. Or a developer uses time-based "random" nonces. On Windows a black console window flashes at every startup. Deployment signs nothing, and every machine is permanently offline.
- **Evidence:** dema4_rs/Cargo.toml:26 (rsa without `getrandom`), :33-34 (windows-sys features only Console + FileSystem); Cargo.lock:3636-3642 (rand_core→getrandom pulled in transitively); dema4_rs/src/main.rs:2 (`windows_subsystem = "windows"`); plans/261030-1009-license-gioi-han-so-lan/phase-01-loi-license.md:35; phase-03-kho-tram-va-bo-khoa-sheet.md:29,43; phase-05-trien-khai-tram.md:23
- **Suggested fix:** Add `getrandom = "0.2"` explicitly (or `rsa` feature `getrandom`) and add `Win32_System_Registry` to windows-sys. Use `RegGetValueW` instead of `reg.exe`, and compute `ma_may()` once in a `OnceLock`. In `license.gs`, normalize the key with `.replace(/\\n/g, "\n")`, and add a `kiemTraKhoa()` self-test function to the deploy steps.

## Finding 10: The Apps Script tests cannot be rerun, two of them prove nothing, and the formatter port has no test oracle once the Rust code is deleted
- **Severity:** Medium
- **Location:** Phase 2 Tests (run with the editor's Run button; `test_dong_thoi`; tests 9–10 "UrlFetch giả"); Phase 2 Architecture (port `noi_dung_thong_ke`, `noi_dung_tach`, `dong_nguong`, 21 columns, mô tả tab to JS); Phase 3 (delete those from Rust); plan.md effort "~5 ngày"
- **Flaw:** Tests are run by hand in the editor against a copied spreadsheet. They are not in CI, there is no clasp/local runner, and they do not go through `doPost` (so the 302, `e.postData.contents`, and content-type are never tested). `test_dong_thoi` sends 10 calls one after another, so it cannot test concurrency. "UrlFetch giả" requires dependency injection into `guiHangDoi`, which the architecture does not mention. `test_soan_tin_telegram` compares against "mẫu Rust hiện tại", but phase 3 deletes those Rust functions (`telegram.rs` → `may.rs`), so the reference disappears and the two copies will drift. Porting 3 formatters, 21 columns, the description tab, CSV, a queue, rate limiting, signing, and 11 tests is not realistic in 1.5 days.
- **Failure scenario:** A later edit to `license.gs` is deployed after nobody reran the editor tests. A real concurrent burst (matrix #16) is the first concurrency test, and it happens in production. The Telegram message format quietly changes from what the downstream "script tổng hợp đọc `may=`" expects.
- **Evidence:** plans/261030-1009-license-gioi-han-so-lan/phase-02-tram-apps-script.md:7,36,44,49,50,53-54; phase-03-kho-tram-va-bo-khoa-sheet.md:32; dema4_rs/src/tach_vb/thong_ke_nguong.rs:134-135 (CSV header consumed by a downstream script); dema4_rs/src/telegram.rs:110,162,192 (formatters to be deleted)
- **Suggested fix:** Keep message/CSV formatting in Rust (still structured and length-capped, since the app is the only legitimate client) and have the station forward it with server-side length and charset checks. Or freeze golden strings from the current Rust output into `apps-script/test-fixtures` before deleting the code. Replace `test_dong_thoi` with an external script that sends 20 parallel POSTs (and make it a phase 5 gate). Put the logic in pure functions that take `fetch`/`sheet` adapters and run them under Node with a Sheet stub so the tests are repeatable. Re-estimate phase 2 at 3+ days.

**Status:** DONE
**Summary:** 10 findings (2 Critical, 5 High, 3 Medium). The biggest risks: retried writes can bill the customer twice when the client times out; the license can be bypassed in the open through old public releases and the service-account key the plan keeps alive; and the machine ID is unstable. The Scope Auditor check found that `KiemTra` is attached to `UngDungChinh` while the gated methods and tests live on `UngDung`/`ManTach`/`chay_tach`, so tests would hit the real network and disk.

**Unresolved questions**
- Is "Anyone" web-app access allowed on the target Workspace (huce.edu.vn vs Sao Mai)?
- Is downgrading to v0.5.x an accepted bypass, or should old release assets be removed?
- Should a stopped Đếm run with partial results count as 1 use? The plan only says "chạy xong và có kết quả".
